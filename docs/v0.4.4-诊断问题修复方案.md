## 1. 结论摘要

| 问题 | 当前结论 | 处理决定 |
| --- | --- | --- |
| 余额变化但没有滚动动画 | 当前 `RollingAmount` 在空闲时卸载轨道，下一次变化才新建节点；“缺少稳定动画起点”是高可信根因，但仍需真实浏览器验收 | 采用常驻轨道，但重新设计动画状态机，不原样复制参考函数 |
| 官方页面为 0、插件仍显示 0.03 | 上游余额口径短暂不同步是主要假设，但事故时没有保存原始响应；客户端刷新失败时保留旧成功值也是已确认的可行路径 | 不伪造或修正金额；把失败旧值、查询时间和数据边界直接显示出来，并保留复现取证入口 |
| `is_available: false` 仍像正常金额 | 已由当前组件结构和只读诊断稳定复现，是独立的显示缺陷 | 主标签显示“余额不足”，状态点/背景改红，保留接口金额并给出充值提示 |
| 分享环境报 `chcp` / `npx` 找不到 | 截图只证明 Windows 命令解析链失败；PATH、PATHEXT、Node 缺失或文件缺失尚不能单独定案 | 重写只读预检和安装器，使用绝对工具路径、严格版本检查、默认离线；缺 pnpm 时仅在用户确认后从固定 registry 引导安装 |
| 保存新 Key 时旧请求仍可能回写 | 源码复核发现的相关竞态：保存后只重置比较并刷新；若旧请求仍在进行，新刷新会被丢弃，旧账号响应可能重新建立基准 | 增加凭据切换专用状态迁移，取消旧请求、清空旧数据显示与比较基准，再发起新查询 |

实施版本为 v0.4.4。旧 v0.4.3 发布物及其哈希保持不变，不用相同版本号重新打包。

## 2. 证据边界

### 2.1 已确认

- v0.4.3 的滚轮轨道在非动画/动画结束状态返回纯文本，轨道不是常驻节点。
- 本轮只读执行滚轮诊断断言 9 项和余额不足显示断言 8 项，均通过。
- 滚轮诊断运行时出现 React `act(...)` 警告，且 jsdom 不会真实绘制 CSS transition；这些测试只能证明 DOM/状态条件，不能替代 Chromium/Harness 目视验收。
- 客户端普通超时/网络错误会保留 `snapshot.data` 与 comparison；主标签继续显示金额和旧差额，只有红色状态及悬停详情表达错误。
- `isAvailable === false` 且余额列表非空时，当前主标签仍优先进入正常金额分支。
- 当前安装器裸调用 `chcp` 和 `where npx`；截图显示这两步的命令解析均失败。
- 当前本机 DSH 插件命令会转发给 `pnpm`，安装器必须把 pnpm 可用性纳入预检。

本轮实施后的新增确认：

- `src/client.js` 已采用常驻滚轮轨道、可取消双 `requestAnimationFrame` 状态机、失败旧值/余额不足标签和 `credentialChanged()` 请求隔离。
- `installer/安装 DeepSeek 余额插件.cmd` 已改为 ASCII、绝对工具解析、Node/PATHEXT/npx/pnpm/SHA256 预检、用户确认的固定版本 pnpm 引导、动态 DSH store 选择和 offline-first；`诊断安装环境.cmd` 只读输出工具路径与版本。
- `npm run check` 已通过，当前自动测试为 33 项；构建同步更新 `client/client.js`。

### 2.2 尚未确认，实施时不得写成事实

- 没有事故时 DeepSeek `/user/balance` 的原始响应，不能证明当时一定返回了 `is_available: true` 与 `0.03`。
- 诊断材料展示的 `ETag` / `Age` 缺失来自本机插件端点，不是上游响应头；当前代码也没有保留上游头，因此不能据此断言上游完全没有新鲜度信号。
- 充值后的余额下降采样只能证明该时间段会更新，不能反推余额耗尽时是否发生短暂不同步。
- 安装截图没有记录 PATH、PATHEXT、Node/npx/pnpm 实际文件和版本，因此不能只凭截图要求用户重装 Node。

对 0.03 事故的正式表述统一为：

> 根据同一 Key 的用户时序和当前转发路径，上游余额口径短暂不同步是当前最符合现象的解释之一；客户端刷新失败后保留旧成功值也是已确认的可能路径。由于缺少事故当时的响应、错误状态和查询时间，根因尚未达到抓包级确认。

## 3. 客户端修复设计

### 3.1 滚轮动画状态机

保留现有精确十进制比较、changeSet、revision、520ms 时长和红色差额逻辑，只重做 `RollingAmount` 的可视状态机。

核心规则：

1. 轨道与 viewport 始终挂载；空闲时两行都渲染最终值，视觉位置为起点。
2. 新 revision 首次渲染时同步按 start 状态输出“旧值在上、最终值在下”，不能先画最终值、再回跳旧值。
3. start/reset 阶段禁用 transition；确认起点样式已经提交后，再通过受控的双 `requestAnimationFrame` 进入 end，并且只在 end 阶段启用 520ms transition。
4. 动画结束后先把两行都换成最终值，再无过渡复位到起点，避免从 `-50%` 到 `0` 的可见反向动画。
5. revision 改变、减少动态效果切换、组件卸载或新结果到达时，必须取消旧 frame 与 timeout；最新结果始终获胜。
6. 不采用参考补丁的“一次性 revision ref 直接短路 effect”方案。依赖值没有变化时 React 本就不会重复运行 effect；强行短路会给 StrictMode、动态切换 reduced-motion 和 cleanup 后重调度留下卡在 start 的风险。
7. 视觉副本保持 `aria-hidden`，屏幕阅读器只读最终金额；减少动态效果时直接显示最终值，但精确红色差额仍可显示。

必须覆盖的动画场景：首次加载、增加、减少、不变、520ms 内连续两次结果、动画中切换减少动态效果、组件卸载、React StrictMode 开发行为、多币种同时变化。

### 3.2 显示状态优先级

`compactLabel`、状态颜色、tooltip 和 aria-label 使用同一套优先级，避免主标签与悬停信息矛盾：

1. Key 缺失/鉴权失败：清空余额与比较基准，显示配置或鉴权错误。
2. 普通刷新失败且保留旧成功数据：显示“查询失败 · 上次余额 ¥X”，使用红色状态；tooltip/ARIA 写明错误原因和“上次成功查询时间”，不得只靠红点表达。
3. 成功结果且 `isAvailable === false`：显示“余额不足 ¥X”，使用红色状态与背景；余额列表为空时显示“余额不足”。
4. 成功结果且 `isAvailable === true`：显示正常金额；空列表显示“余额为空”。
5. 没有数据且正在查询：显示“查询中”。

只对明确布尔值 `isAvailable === false` 判定余额不足，字段缺失或响应异常继续走安全错误，不误报业务状态。不可用结果不产生滚轮或扣款差额，并重置可比较基准；恢复后的第一次成功查询只建立新基准。

### 3.3 时间与余额新鲜度

- 把“更新时间”改为“查询时间”；普通失败保留旧数据时改为“上次成功查询时间”。
- tooltip 增加简短说明：“金额来自 DeepSeek 余额接口，可能与控制台短暂不同步。”这说明数据来源和边界，不声称已经证明上游滞后。
- `fetchedAt` 继续表示插件完成成功查询的本地时间，不能描述为上游数据生成时间。
- 不自行把 0.03 改成 0，不按固定阈值宣称“余额不足”，不把 402 之外的现象推断成真实可用性。
- 暂不增加低余额阈值。若未来增加，只能命名为“低余额提醒”，并由用户配置，不能替代接口金额或 `is_available`。

若问题再次出现，取证只记录：本地时间、成功/失败状态、安全错误码、`isAvailable`、各币种金额、`fetchedAt` 和官方页面截图时间。不得打印 API Key、Authorization、credentials 文件内容或完整环境变量。访问真实 DeepSeek 接口仍需用户明确允许。

### 3.4 Key 更新竞态

给 `balanceStore` 增加单一的 `credentialChanged()`（命名可在实现时调整），由保存成功回调调用：

1. 递增请求序号并 abort 旧请求，使旧 Key 的迟到响应失效。
2. 清空 request、旧余额、错误、lastAttempt、baseline、changeSet，并递增 revision。
3. 发布无旧账号数据的非加载快照。
4. 立即用新凭据强制查询；第一次成功只建立基准，不显示跨账号扣款。

插件外部直接改 credentials/环境变量仍无法在页面内可靠识别；这类更新要求刷新页面或重启 Harness。不能通过 Key 指纹传到前端来解决。

## 4. 安装器修复设计

### 4.1 环境预检

安装器保持纯 ASCII，不再调用 `chcp`，也不启用全局 delayed expansion。安装前分别解析并验证：

- `%SystemRoot%\System32\where.exe` 等系统工具是否实际存在；不依赖裸 `where`。
- PATH 与 PATHEXT 是否具备 `.COM`、`.EXE`、`.CMD` 的正常命令解析能力。
- `node.exe` 的绝对路径和版本，严格满足项目 engines：`^22.19.0 || >=24.0.0`，不接受 22.0–22.18 或 Node 23。
- `npx.cmd` 的绝对路径；优先与已确认的 Node/npm 同目录匹配。
- `pnpm.cmd` 的绝对路径与可执行版本。当前 DSH 子进程需要在 PATH 上找到 pnpm，因此只把已验证目录临时加入本次脚本进程 PATH，不永久修改用户环境。
- 插件 `.tgz` 与校验文件存在且版本一致。

各失败类型给出不同错误：系统命令解析异常、Node 未安装、Node 版本不兼容、npx 缺失、pnpm 缺失、包缺失、哈希不一致、DSH 安装失败。安装器不自动安装 Node；缺少 pnpm 时先展示 registry、固定版本和影响范围，只有用户明确选择 `Y` 才执行一次带 `--ignore-scripts` 的 `npm install --global pnpm@11.19.0`，选择 `N` 或安装失败即停止，不自动重试，也不修改系统 PATH。

另提供只读的 `诊断安装环境.cmd`。默认只输出工具是否存在、脱敏后的解析路径、版本和 DSH profile/cache 状态；不输出完整 PATH、credentials 内容、Key 指纹或其他环境变量值。需要更详细信息时由用户在本机查看，不要求把未经审查的完整环境转发给他人。

### 4.2 离线与联网边界

- 保留 `--ignore-scripts`。
- npx 调用同时使用 `--offline --no-install`，避免 npx 为解析 DSH CLI 自行访问 registry；若本机缓存不完整，安装应明确失败而不是联网补包。
- pnpm 引导是唯一允许的可选网络步骤，固定使用 `https://registry.npmjs.org/` 和 `pnpm@11.19.0`；引导成功后本地插件安装仍使用 `--offline --no-install`。
- 删除硬编码 `.dsh\.pnpm-store\v11`；通过已解析 pnpm/当前 DSH 环境查询并验证实际 store，不把脚本绑定到 pnpm 大版本目录。
- 采用 offline-first：默认只安装本地 `.tgz` 并带 `--offline`。若缓存条件不满足，明确停止并说明缺少哪一层缓存。
- 不自动去掉 `--offline` 重试。需要联网的准备或重试必须由用户主动选择并明确知道将访问 npm/DSH 依赖源。
- “插件 `.tgz` 是本地自包含包”不等于“npx、DSH、pnpm 整条工具链在新电脑上无需任何缓存”；INSTALL.md 必须明确这个区别。
- 最终离线参数只有在临时 `DSH_HOME` 的空缓存/已有缓存矩阵通过后才定稿，测试不得触碰真实 profile。

### 4.3 版本与分发

- 从 `package.json.version` 生成安装器目标包名、SHA256 文件名和发布 ZIP 清单，避免脚本手写 0.4.3 后漂移。
- 外层安装器与诊断脚本不再作为插件运行时内容塞进 `.tgz`；由发布组装脚本与 `.tgz`、`.sha256`、INSTALL.md 一起组成 ZIP。
- 安装命令的非零退出码原样透传，窗口保留完整错误；成功才返回 0。
- v0.4.4 安装后移动/删除解压目录，再重启 Harness 并执行一次后续 profile 操作，确认 profile 不依赖临时 `.tgz` 路径。
- GitHub Release 只有在用户明确授权后才创建或更新。

## 5. API Key 安全边界

- Key 来源仍限定为服务端 DSH `credentials` 服务和启动环境变量 `DEEPSEEK_API_KEY`；环境变量来源为只读，页面不能覆盖。
- 页面保存文件型 Key 后，通过 `credentialChanged()` 取消旧请求、清空旧账号数据显示和比较基准，再查询新账号。
- 前端只接收 `configured` / `writable` / `source` 等状态以及余额响应，永远不接收、回显或记录 Key。
- Key、Authorization、credentials 文件内容不得进入浏览器端、日志、诊断输出、测试夹具、仓库、`.tgz`、ZIP 或安装器。
- 自动测试不请求真实 DeepSeek API；真实联调由用户提供运行环境并明确允许。

## 7. 测试与验收

### 7.1 自动测试

- 首次余额不动画；100.00 → 99.00 恰好一次滚动并显示精确 `-¥1.00`；增加只滚动不显示绿色差额；不变不动画。
- 动画首帧不闪最终值，结束后不反向滚动；快速连续结果只停在最新值。
- reduced-motion 初始开启与动画途中开启都立即落到最终值；卸载后无 frame/timer 更新。
- 普通失败保留数据时主标签含“查询失败/上次余额”，不保留正常态观感；恢复成功后按最后成功基准继续比较。
- `isAvailable === false` 覆盖非零、零、空列表、多币种及中英文；均无动画/差额，颜色和文字一致。
- 保存新 Key 时旧请求迟到也不能回写；新 Key 第一次成功不产生跨账号差额。
- 既有十进制字符串 + BigInt、Key 缺失/鉴权失败、币种集合变化测试继续通过。
- 安装器静态契约：无 chcp、无裸 where、无全局 delayed expansion、无硬编码 v11、版本单一来源、保留 `--ignore-scripts`、错误码透传。
- 安装器动态矩阵（待在隔离临时目录执行）：PATH 缺 System32、PATHEXT 损坏、Node 缺失/过旧/不在 PATH、npx 缺失、pnpm 缺失/损坏、用户拒绝 pnpm 引导、pnpm 引导失败、路径含空格/中文/`!`、包/哈希缺失、成功与任意非零退出码。

### 7.2 集成与人工验收

- `npm run check` 全通过，且不访问真实 DeepSeek API。
- 在临时 `DSH_HOME` 验证安装器的空缓存、已有缓存、升级、退出码和移动解压目录场景；不得改真实 profile。
- 在真实 Chromium/Harness 顶栏用受控模拟数据观察 100 → 99、99 → 101、快速连续变化、多币种、窄屏和 reduced-motion；仅有自动断言不算动画验收完成。
- 经用户明确允许后，才可在用户运行环境中验证真实余额；差异复现时只采集第 3.3 节定义的安全字段。
- 用户明确同意安装候选后，才更新本机官方 `web` profile；发布仍需另行明确授权。

## 8. 验收标准

- 最终显示金额始终等于最近一次成功接口返回值；失败保留值必须明确标为上次结果，不能伪装成当前余额。
- 上游明确不可用时，主标签直接显示“余额不足”，而非只显示金额或仅靠颜色提示。
