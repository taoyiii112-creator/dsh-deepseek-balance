# v0.4.7 安装器 pnpm 存储目录继承修复方案

> **历史版本档案：** 本文诊断的是 v0.4.7 Web profile 自制安装器，不是 v0.6.1 Desktop 插件页安装故障。当前 Desktop 由 Electron 所有 `desktop` profile，并通过主应用插件管理器安装；详见 [v1.0.1 Desktop 兼容说明](v1.0.1-Desktop兼容说明.md)。

## 问题与原因

0.4.7 安装器能找到并执行 `pnpm.cmd`，但没有让该 pnpm 沿用目标 `web` profile 已存在的 store。pnpm 在 `node_modules/.modules.yaml` 中记录当时的 `storeDir`；本机记录为 本机 pnpm store 路径。安装器启动的 pnpm 默认选择 `AppData\Local\pnpm\store\v11`，因此升级已有 profile 时触发 `ERR_PNPM_UNEXPECTED_STORE`。这是两个独立的检查：可执行文件位置不决定依赖存储位置。

## 修复

1. 在修改目标 profile 前读取其 `node_modules/.modules.yaml`。没有该文件时视为全新安装，沿用 pnpm 自身设置。
2. 有该文件时，只接受单一、绝对路径、末段为 pnpm 版本目录 `v数字` 的 `storeDir`；格式不符合预期即停止并说明，不猜测或删除原 `node_modules`。
3. 从记录的 `storeDir` 推出配置根目录，仅在安装器启动的 pnpm 与 DSH 子进程环境中设置 `PNPM_CONFIG_STORE_DIR`。执行 `pnpm store path` 并与原记录比对；不一致则在安装前停止。
4. 不修改用户全局 pnpm 设置、不硬编码本机用户名或 store 版本；继续按现有规则寻找安全的 pnpm 可执行文件，不自动执行未预置的 Corepack shim。

## 验证与交付

- 模拟已有 profile 使用非默认 store，确认安装器传入旧 store，并成功升级。
- 模拟全新 profile，确认不会强加旧 store；异常或不匹配的元数据必须在安装前失败。
- 通过项目 check 与安装器包内回读，生成新后缀 ZIP，保留现有 `review` 包以免覆盖用户已安装的 0.4.7。真实 profile 不为验证而重复安装；新 ZIP 待用户实际分发前完成独立验收。

## 执行结果

隔离升级、全新安装与存储目录不匹配分支已通过自动回归。最终本地分享包按用户要求改为 `release/dsh-deepseek-balance-0.4.7-安装包.zip`；旧 `review`、`storefix`、`storefix2` 候选和重复构建归档已移入 Windows 回收站。真实 `web` profile 仍安装同一份 0.4.7 插件归档，未重复安装；真实页面视觉验收与正式发布仍待完成。
